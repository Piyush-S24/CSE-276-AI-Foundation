1Softmax, temperature and entropy

How a language model turns scores into a choice — and how one dial changes its whole character.

Softmax and entropy
pj = exp(zj / T) ∑k exp(zk / T),   H = − ∑i pi log2 pi
Divide the logits by T before exponentiating. Entropy measures how undecided the result is: 0 bits means certain.
The method — what to actually do
  1. Divide every logit by T.
  2. Subtract the largest value from all of them (numerically safer, mathematically identical).
  3. Exponentiate each.
  4. Sum them, then divide each by the sum. Check the result adds to 1.
  5. For entropy: − ∑  p log2 p. Use log2p = ln p / ln 2.
  6. Terms with p = 0 contribute 0.
  7. Maximum entropy for N options is log2 N.
Worked example — the same logits at three temperatures
After “the cat sat on the…” the model outputs logits: mat 4.2, floor 3.1, chair 2.6, roof 1.4, banana −0.8.
  1. At T = 1, exponentiatee4.2 = 66.69, e3.1 = 22.20, e2.6 = 13.46, e1.4 = 4.06, e−0.8 = 0.45
  2. Sum = 106.85, then dividemat 66.69106.85 = 62.4%, floor 20.8%, chair 12.6%, roof 3.8%, banana 0.4%
  3. Entropy at T = 1−[0.624 log 0.624 + 0.208 log 0.208 + …] = 1.484 bits
  4. At T = 0.2, every logit is multiplied by 5 first21.0, 15.5, 13.0, 7.0, −4.0 → gaps magnified → mat 99.6%, entropy 0.043 bits
  5. At T = 2.0, every logit is halved2.1, 1.55, 1.3, 0.7, −0.4 → mat 42.5%, floor 24.5%, chair 19.1%, roof 10.5%, banana 3.5%
  6. Entropy at T = 21.988 bits, against a maximum of log2 5 = 2.322
  7. What never changedthe logits — the model's beliefs were identical in all three cases
62.4% → 99.6% → 42.5% for the same model. At T = 0.2 the output is effectively deterministic; at T = 2.0 “banana” has a 1-in-29 chance of being emitted. Temperature belongs in every bug report.
Practice
  1. Logits 3, 1, 0 at T = 1. Compute the softmax.
    e3 = 20.086, e1 = 2.718, e0 = 1.000; sum = 23.804. → 0.844, 0.114, 0.042. They sum to 1.000 ✓
  2. What is the entropy of a distribution that puts probability 1 on one option?
    −1 log21 = −1(0) = 0 bits. Zero entropy means no uncertainty at all — the model will always emit the same token. This is what T → 0 approaches.
  3. Why subtract the maximum logit before exponentiating?
    To avoid numerical overflow. With logits around 800, e800 exceeds the range of a floating-point number and becomes infinity. Subtracting the max makes the largest exponent 0, so e0 = 1 and everything else is smaller. The probabilities are mathematically identical, because the constant cancels between numerator and denominator.

2Cosine similarity and retrieval

The arithmetic behind RAG: find the stored passages whose meaning is closest to the question.

Cosine similarity
cos(a, b) = a·b‖a‖ ‖b‖ =  ∑iaibi√ ∑iai2 √ ∑ibi2
Measures the angle only, so a long document and a short query can still match on topic. Range −1 to 1; for text embeddings, usually 0 to 1.
The method — what to actually do
  1. Compute the dot product: multiply component by component and sum.
  2. Compute each vector's magnitude: square the components, sum, square root.
  3. Divide the dot product by the product of the two magnitudes.
  4. Repeat for every stored vector.
  5. Sort descending and keep the top k.
  6. Sanity checks: cos = 1 means identical direction, 0 means orthogonal (unrelated).
  7. Both vectors must come from the same embedding model, or the comparison is meaningless.
Worked example — retrieving the right passage
Query “Can I send this back?” embeds to q = (0.88, 0.20, 0.07). Two candidates: D2 “return window” = (0.86, 0.25, 0.10) and D5 “staff holidays” = (0.05, 0.10, 0.96).
  1. Dot product with D20.88(0.86) + 0.20(0.25) + 0.07(0.10) = 0.7568 + 0.0500 + 0.0070 = 0.8138
  2. Magnitude of q√0.7744 + 0.0400 + 0.0049 = √0.8193 = 0.9052
  3. Magnitude of D2√0.7396 + 0.0625 + 0.0100 = √0.8121 = 0.9012
  4. Cosine with D20.81380.9052 × 0.9012 = 0.81380.8158 = 0.9977
  5. Dot product with D50.88(0.05) + 0.20(0.10) + 0.07(0.96) = 0.0440 + 0.0200 + 0.0672 = 0.1312
  6. Magnitude of D5√0.0025 + 0.0100 + 0.9216 = 0.9665
  7. Cosine with D50.13120.9052 × 0.9665 = 0.13120.8749 = 0.1500
  8. Note what made it workthe query shares no words with “return window” — keyword search would have returned nothing
0.9977 versus 0.1500. The match is entirely on meaning, which is precisely what makes retrieval-augmented generation possible and what keyword search cannot do.
Practice
  1. Compute cos between (1, 0) and (0, 1).
    Dot = 1(0) + 0(1) = 0. Magnitudes both 1. cos = 0/1 = 0 — perfectly orthogonal, i.e. completely unrelated.
  2. Compute cos between (3, 4) and (6, 8).
    Dot = 18 + 32 = 50. Magnitudes √25 = 5 and √100 = 10. cos = 50/50 = 1.000 — the second vector is just the first doubled, so the direction is identical and cosine ignores the length entirely.
  3. You index your documents with embedding model X and query with model Y. What happens?
    The vectors live in different spaces, so the similarities are meaningless. Nothing will error — you simply get quietly irrelevant results, which is the dangerous part. Changing embedding model means re-indexing the entire corpus.

3Fairness metrics across groups

The same confusion-matrix arithmetic, done per group — which is where aggregate metrics hide the problem.

Three rates, computed per group
TPR = TPTP+FN,  FPR = FPFP+TN,  PPV = TPTP+FP
Equal PPV across groups is calibration. Equal FPR and FNR is equalised odds. With different base rates you cannot have both.
The method — what to actually do
  1. Split the data by group and build a separate confusion matrix for each.
  2. Compute accuracy, precision, TPR and FPR for each group independently.
  3. Compare them side by side — never aggregate at this stage.
  4. Compute the ratio of each metric between groups; a ratio far from 1 is the finding.
  5. Check the base rates (positives / total) — if they differ, the impossibility result applies.
  6. State which fairness criterion you are equalising, and why that one.
  7. Report the per-group table, not just the gap.
Worked example — a calibrated model that is still unfair
Two groups of 100. Group H has base rate 60% (60 genuinely positive); group L has 25%.
H: TP=52, FP=7, FN=8, TN=33.  L: TP=14, FP=2, FN=11, TN=73.
  1. AccuracyH = 52 + 33100 = 0.850; L = 14 + 73100 = 0.870 → near identical
  2. Precision (PPV)H = 5259 = 0.881; L = 1416 = 0.875 → the model is calibrated
  3. So far it passes every usual check. Now FPRH = 740 = 0.175; L = 275 = 0.027
  4. The ratio0.1750.027 = 6.6× — an innocent person in group H is flagged six times more often
  5. And FNRH = 860 = 0.133; L = 1125 = 0.440 → ratio 3.3×
  6. Why this cannot be tuned awaywith different base rates, equalising PPV forces FPR and FNR apart — Chouldechova's impossibility result
Equal accuracy, equal precision, yet 6.6× the false-positive rate for one group and 3.3× the miss rate for the other. Both groups are harmed, in opposite ways, by a model that passes every aggregate check. The only honest response is to choose which error matters more and publish the per-group numbers.
Practice
  1. Group A: TP=30, FP=20, FN=10, TN=40. Compute TPR, FPR and PPV.
    TPR = 30/(30+10) = 0.750. FPR = 20/(20+40) = 0.333. PPV = 30/(30+20) = 0.600.
  2. Group B has the same accuracy as group A but FPR 0.08 against A's 0.33. Is the model fair?
    No. Equal accuracy conceals a 4× difference in how often innocent members of each group are wrongly flagged. Accuracy averages over both error types and both classes, so it can stay constant while the composition changes completely. Always report per-group FPR and FNR.
  3. Why can a model not have equal precision, equal FPR and equal FNR across two groups with different base rates?
    Because the three are algebraically linked through the base rate: PPV can be written in terms of TPR, FPR and the base rate. Fix any two and the third is determined — so if the base rates differ, matching all three is impossible unless the classifier is perfect. This is a theorem, not an engineering shortfall.
